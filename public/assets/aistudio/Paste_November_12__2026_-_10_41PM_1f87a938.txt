The objective is not to recreate Hades. It is to understand the systems that make Hades work and translate those systems into Kaliyuga's own identity.

There is one important scope decision:

Vertical-slice scope locked

We are focusing on the existing vertical slice:

1. Five-scroll prologue and opening.
2. Vaitarani Ferry Ghat hub.
3. Savitri and the weaponsmith interactions.
4. Act I – Charnel Plains.

7. Vrikodara boss.

The biggest difference is the combat philosophy.

Hades prioritizes fast, continuous action. Kaliyuga can have heavier attacks, more deliberate enemy encounters and greater emphasis on boss pattern recognition.

We should borrow Hades' responsiveness without necessarily copying its attack speed.

## 2. The development philosophy we should adopt

Hades was built around interconnected systems, rather than hundreds of disconnected features.

Its art direction also evolved around production feasibility. Jen Zee explained that Supergiant moved from a painterly approach to pen-and-ink partly because it was faster to produce at the scale they needed.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://mcvuk.com\&sz=32)

MCV/DEVELOP+1



There are three principles I want to carry into Kaliyuga:

Principle A — System depth over content quantity.

Make existing enemies, attacks, upgrades and bosses interesting before producing more.

Principle B — Every action must communicate.

Movement, attacks, parries, enemy telegraphs and damage should be understandable visually and through sound.

Principle C — Production consistency.

Every asset must fit a defined pipeline. We should not have to redesign the game every time we introduce a new enemy.

## 4. Rudra's movement system

[Critique de Hades : chef d’oeuvre de l’action – Etoile et champignon](https://images.openai.com/static-rsc-4/fdrvcMgEwxCikT795Y9SwRBm6M7SJ5lyuhhBzO_giNuA0rsRsm-4LdMmh8cwjMHBmVGfKUWdb2DYIh7J0zPwjgpscybT-TEI4nxG5I6DXBUwK4NDvm2YzTsNWcH0jGTlePHAssunXPOkI3wtPwqQxEJ7dHss9AeGGxNy1y8e-cU?purpose=inline)

[etoile-et-champignon.fr](https://etoile-et-champignon.fr/critique-de-hades-chef-doeuvre-de-laction/?utm_source=chatgpt.com)

Movement is the foundation of combat.

A player should never feel that the character is fighting against their input.

### Required movement states

| State           | Expected behaviour              |
| --------------- | ------------------------------- |
| Idle            | Stable standing animation       |
| Moving          | Directional movement            |
| Turning         | Smooth directional transition   |
| Dash            | Fast directional movement       |
| Attack movement | Appropriate movement commitment |
| Hit reaction    | Temporary movement interruption |
| Stagger         | Reduced or disabled control     |
| Death           | Controlled death sequence       |

### Movement requirements

- Consistent movement speed.
- Smooth directional changes.
- No unwanted acceleration.
- Reliable collision with the playable floor.
- Correct foot anchoring.
- No slipping during idle.
- No animation overriding combat input.
- No movement through solid enemies or obstacles unless explicitly intended.

### Dash design

Hades makes the dash a central combat action.

For Rudra, it should provide:

- A clear movement burst.
- A controlled duration.
- An intentional recovery window.
- A defensive window if that is part of the existing design.
- Consistent directional input.
- Reliable interaction with enemy hitboxes.

I recommend keeping dash invulnerability and dash distance as separate tuning parameters.

That lets us balance defensive effectiveness without accidentally changing movement feel.

### Acceptance criteria

- Rudra responds to movement input immediately.
- Dash does not cause unintended animation locking.
- Dash cannot be spammed indefinitely if the current design requires stamina or cooldown restrictions.
- Rudra cannot become stuck in a dash state.
- Movement remains consistent throughout every chamber.

9

We should treat the Parashu as one weapon with multiple combat behaviours.

We do not need six weapon types.

We need one exceptionally polished weapon.

### Proposed attack structure

| Attack         | Function                              | Design purpose           |
| -------------- | ------------------------------------- | ------------------------ |
| Light attack 1 | Quick horizontal strike               | Fast initiation          |
| Light attack 2 | Follow-up strike                      | Combo continuation       |
| Light attack 3 | Stronger finishing strike             | Combo payoff             |
| Heavy attack   | Committed powerful strike             | High impact              |
| Heavy charge   | Stronger attack, if already supported | Risk/reward              |
| Dash attack    | Mobile offensive strike               | Repositioning            |
| Parry          | Defensive counter                     | Timing mastery           |
| Stance attack  | Existing stance-specific variation    | Combat identity          |
| Astra          | Existing ability                      | Powerful tactical moment |

These are the target behaviours, not a requirement to implement every missing move during the vertical slice.

### Attack state architecture

```

IDLE
  |
  +--> LIGHT_ATTACK_1
  |       |
  |       +--> LIGHT_ATTACK_2
  |               |
  |               +--> LIGHT_ATTACK_3
  |
  +--> HEAVY_ATTACK
  |
  +--> DASH
  |
  +--> PARRY
  |
  +--> STANCE_ACTION
  |
  +--> ASTRA_ACTION
  |
  +--> HIT_REACTION
  |
  +--> STAGGER
  |
  +--> DEATH

```

Every attack should have three timing windows:

- Startup: attack preparation.
- Active: damage can connect.
- Recovery: attack finishes and control returns.

This prevents the common problem of animations playing while the actual hitbox behaves independently.

### Combo buffering

Hades feels responsive partly because the game does not require the player to press every input at an exact frame.

For Kaliyuga, we should test a small input-buffer window.

For example:

If the player presses the next attack slightly before the current attack finishes, the game queues it and executes it when the next combo window opens.

This avoids requiring frame-perfect button presses.

### Attack cancellation

Not every action should cancel every other action.

I recommend:

| From         | Can transition into                  |
| ------------ | ------------------------------------ |
| Idle         | All valid actions                    |
| Light attack | Next combo, permitted dash           |
| Heavy attack | Recovery, permitted defensive action |
| Dash         | Idle, permitted follow-up            |
| Parry        | Counter or recovery                  |
| Hit reaction | Recovery when reaction ends          |
| Stagger      | Recovery when posture permits        |
| Death        | Nothing                              |

The final rules should be based on the existing combat implementation rather than creating conflicting state systems.

8

This is where many indie action games fail.

An attack can have a beautiful animation and still feel terrible if the enemy doesn't respond correctly.

Hades communicates impact using several simultaneous feedback layers.

For Kaliyuga, we should establish the following hit-confirmation pipeline:

Rudra attack connects

Hitbox confirms collision

Damage calculation

Damage, armour, posture and modifiers

Enemy reaction

Hit animation, stagger, knockback

Player feedback

Impact VFX, sound, optional hitstop

### Required feedback layers

| Feedback                    | Priority   |
| --------------------------- | ---------- |
| Correct enemy hit reaction  | Critical   |
| Correct damage registration | Critical   |
| Weapon impact sound         | Critical   |
| Visible impact effect       | High       |
| Hitstop on selected attacks | High       |
| Knockback                   | High       |
| Stagger response            | High       |
| Damage numbers              | Optional   |
| Screen shake                | Controlled |

### Hitstop

Hitstop is a very short pause or slowdown around a successful impact.

It can make heavy attacks feel substantially more powerful.

But it should be used selectively.

For example:

- Light attacks: little or no hitstop.
- Heavy attacks: stronger hitstop.
- Boss finishing attacks: more pronounced impact.
- Environmental attacks: context-dependent.

These are tuning principles, not final frame values. We should determine actual timing through playtesting.

Our target: Rudra's attacks should feel like they physically connect with something.

Hades doesn't need every enemy to have extremely sophisticated artificial intelligence.

It gives enemies recognizable roles and combines those roles to create challenging encounters.

We should use the same principle.

### 7.1 Four fundamental enemy roles

We can classify our existing enemy assets into these behavioural roles. This does not require adding new enemies.

| Role                | Behaviour               | Player challenge     |
| ------------------- | ----------------------- | -------------------- |
| Basic melee         | Approaches and attacks  | Basic combat         |
| Heavy melee         | Slow, powerful attacks  | Timing and parrying  |
| Ranged              | Attacks from distance   | Positioning          |
| Aggressive/charging | Rapidly closes distance | Movement and dodging |

Some existing enemies can combine two roles.

### 7.2 Enemy state machine

Every regular enemy should use a consistent state architecture.

```

SPAWN
  |
  v
IDLE
  |
  v
DETECT PLAYER
  |
  v
APPROACH / POSITION
  |
  v
SELECT ATTACK
  |
  v
TELEGRAPH
  |
  v
ATTACK
  |
  v
RECOVERY
  |
  +----> SELECT ATTACK
  |
  +----> REPOSITION

INTERRUPT STATES:
  HIT REACTION
  STAGGER
  KNOCKBACK
  DEATH

```

### 7.3 Enemy behaviour requirements

Detection

- Detect Rudra within a defined radius.
- Stop detecting when outside the relevant range.
- Avoid activating enemies across the entire map unnecessarily.

Positioning

- Approach the player.
- Maintain an appropriate attack distance.
- Avoid stacking all enemies at the same coordinates.
- Avoid continuously pushing against one another.

Attack selection

- Select an attack appropriate to distance.
- Respect attack cooldowns.
- Avoid overlapping attacks from every enemy simultaneously.
- Avoid enemies repeatedly selecting attacks that cannot connect.

Recovery

- Give the player an opportunity to respond.
- Avoid instant repeated attacks.
- Make attack patterns recognizable.

### 7.4 Coordinated enemy waves

This is something I particularly recommend borrowing from Hades.

Rather than spawning all enemies simultaneously and letting them independently attack Rudra, use controlled encounter groups.

Example:

Example encounter composition

Wave 1 — Introduction

Two basic melee enemies.

Tests the player's basic attack and movement.

Wave 2 — Pressure

Two melee enemies and one ranged enemy.

Forces the player to manage multiple directions.

Wave 3 — Challenge

One heavy enemy and supporting melee enemies.

Tests parrying, stagger and attack timing.

Completion

All enemies defeated, reward unlocked.

These are example configurations, not additional content requirements. Use the existing Charnel Plains roster.

Important: Don't let every enemy attack simultaneously. Give the encounter an attack rhythm.

The player should feel pressured, not cheated.

### 9.1 The Kaliyuga chamber loop

Enter chamber

Environment and camera initialization

Encounter begins

Enemy spawning and combat activation

Combat

Enemy waves and existing combat systems

Encounter completion

Verify that all enemies are defeated

Reward / progression

Next chamber or boss

### 9.2 Room design rules

Every chamber should have a specific gameplay purpose.

I recommend these categories:

| Chamber type    | Purpose                                  |
| --------------- | ---------------------------------------- |
| Introduction    | Introduce enemies and basic combat       |
| Standard        | Test familiar mechanics                  |
| Mixed encounter | Combine different enemy roles            |
| Elite           | Test combat mastery                      |
| Boss            | Test learned mechanics                   |
| Reward          | Provide progression and narrative payoff |

These are functional categories, not a demand for more levels.

### 9.3 Arena layout

Every combat arena should be checked for:

- Adequate playable space.
- Clear enemy spawning positions.
- Reliable collision boundaries.
- Camera visibility.
- No hidden player position.
- No enemy spawning inside the player.
- No inaccessible corners.
- No collision with decorative scenery.
- Enough room for boss attacks.

Critical: Our playable floor must be independent of the animated background.

This is particularly important for our 2.5D implementation.

We have chosen a different rendering direction.

Our current structure is:

- Rudra: 3D.
- Regular enemies: 2D sprite sheets.
- Environments: painted backgrounds.
- Environment animation: video or animated visual layers.
- Bosses: existing mixed presentation.

## 10.1 Five-layer visual architecture

Layer 5 — Foreground

Foreground props, atmospheric effects, occlusion.

Layer 4 — Characters

3D Rudra, 2D enemies, boss models or sprites.

Layer 3 — Combat effects

Weapon trails, impact effects, attacks and projectiles.

Layer 2 — Playable floor

Collision, navigation, enemy movement and attack positioning.

Layer 1 — Animated background

Painted environment, fire, water, smoke and distant scenery.

The actual rendering order should be configurable per scene. The five layers describe functional responsibilities, not an inflexible draw-order rule.

### 10.2 Rudra and enemy integration

The most significant technical risk is the combination of a 3D player and 2D enemies.

They need to look like they occupy the same world.

We should test:

- Character scale.
- Foot position.
- Ground contact.
- Shadow placement.
- Lighting consistency.
- Outline and colour consistency.
- Camera perspective.
- Movement speed.
- Attack reach.
- Hitbox alignment.

The 3D Rudra model should not be replaced with a 2D sprite simply because of one visual mismatch.

First test the existing model against the enemy sprites and correct the scale, lighting, camera and rendering.

Only reconsider pre-rendering if the mismatch persists.

Our current sprite pipeline uses approximately 14 existing enemy/boss sheets, with 8×6 or 10×6 layouts as appropriate.

The integration pipeline should be:

1. Import sprite sheet.
2. Verify frame dimensions.
3. Verify transparent regions.
4. Configure animation frame sequences.
5. Extract idle, movement, attack, hit and death animations where available.
6. Align the character's feet.
7. Set a consistent ground anchor.
8. Configure collision.
9. Configure Y-sorting.
10. Test against Rudra.

### Non-negotiable sprite requirements

- No jumping between ground positions during animation.
- No accidental cropping.
- No visible sprite sheet grid.
- No inconsistent animation speed.
- No incorrect direction flipping.
- No floating characters.
- No enemy hitbox detached from the character.

### Y-sorting

In an isometric game, the rendering order must respond to character position.

For example, a character closer to the bottom of the screen may need to render in front of another character farther up the screen.

This must be consistent for:

- Rudra.
- Enemies.
- Bosses.
- Props.
- Foreground elements.

### Foot anchoring

The foot position should be the reference point for character placement.

This prevents a character from appearing to slide or jump when its animation changes.

### Progression categories

| Category           | Purpose                               |

| Temporary reward   | Improves the current expedition       |

### The quality test

Every upgrade should pass at least one of these tests:

- Does it change the player's combat strategy?
- Does it improve an existing mechanic meaningfully?

If an upgrade only adds a negligible numerical increase, it is lower priority.

Its central strength is how the content interacts.

This is why I would rather have five interesting, tested upgrades than twenty upgrades that barely change combat.

### 14.1 Two presentation systems

I recommend keeping two distinct presentation formats.

A. Illustrated narrative cutscenes

- Painted cinematic compositions.
- Multiple deliberately composed shots.
- Subtle camera movement.
- Controlled animation.
- Atmospheric music.
- No unnecessary character animation.
- No artificial AI-generated movement that distracts from the artwork.

B. In-game interactions

- Savitri's chat-style interface.
- Weaponsmith interaction.
- Mission updates.
- Short lore entries.
- Reward descriptions.
- Narrative progression notifications.

This creates a distinction between major story moments and ordinary hub interactions.

### 14.2 Selective boss cinematics

Boss introductions deserve more presentation than regular enemies.

However, we shouldn't create a cinematic for every encounter.

I recommend:

- Dundubhi: dedicated entrance.
- Vrikodara: dedicated entrance.
- Regular enemy waves: direct gameplay.
- Boss phase transitions: gameplay animations and effects.
- Boss defeats: dedicated short sequences where appropriate.

The player's control should return quickly after important cinematic moments.

### 14.3 Narrative flags

The game needs reliable state tracking.

For example:

```
PROLOGUE_COMPLETED
OPENING_COMPLETED
VAITARANI_ENTERED
LANTERN_STATE_UPDATED
ACT_I_STARTED
DUNDUBHI_DEFEATED
VRIKODARA_DEFEATED
FIRST_SHARD_COLLECTED
MEMORY_UNLOCKED
SANJAYA_CORRECTION_1
FERRY_I_COMPLETED
```

These are suggested names for existing story milestones, not an instruction to create duplicate progression systems.

The game should use a single source of truth for these flags.

This prevents:

- Dialogue repeating incorrectly.
- Bosses reappearing after defeat.
- Rewards being granted twice.
- Cutscenes triggering in the wrong order.
- Progression getting stuck.

### 16.1 The most important architectural rule

Do not let individual enemies implement their own completely separate damage and combat logic.

All enemies should use the same fundamental combat interface.

For example:

```
ReceiveHit(
    damage,
    posture_damage,
    knockback,
    attack_type,
    source_position
)
```

The enemy then decides how to respond based on its current state and resistance.

Dundubhi and Vrikodara can have special responses, but they should still use the shared foundation.

### 16.2 Data-driven attack configuration

Rather than hardcoding every attack into separate scripts, use configuration data.

Illustrative example:

```
{
  "attack_id": "rudra_heavy_01",
  "damage": 40,
  "posture_damage": 30,
  "startup": 0.35,
  "active": 0.18,
  "recovery": 0.55,
  "knockback": 5.0,
  "hitstop": 0.08
}
```

These values are hypothetical examples, not recommended final balance numbers.

The benefit is that an AI coding agent or designer can tune attacks without rewriting the entire combat system.

### 16.3 One source of truth

The following should not be duplicated:

- Player health.
- Stamina.
- Posture.
- Astra Energy.
- Boss health.
- Boss phase.
- Enemy health.
- Story flags.
- Reward state.

The HUD should read from the underlying gameplay systems rather than maintaining separate copies of those values.

This avoids bugs where the visual health bar and actual health disagree.

# PART X — Production pipeline

## 17. How Hades' production decisions apply to us

Jen Zee's account of Hades' production reveals something particularly useful: the art pipeline was selected with the volume of required assets in mind.

Supergiant shipped 32,494 FX animation frames and 942,489 character and enemy animation frames, alongside its extensive character and environment art.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://mcvuk.com\&sz=32)

MCV/DEVELOP



We have a much smaller vertical-slice scope.

We should optimize around the assets already generated.

### 17.1 Our asset pipeline

1\. Asset generation

Character artwork, sprite sheets, backgrounds and VFX.

2\. Asset validation

Transparency, proportions, frames, consistency and dimensions.

3\. Engine integration

Animation, collision, sorting, positioning and rendering.

4\. Gameplay testing

Combat, readability, animation transitions and performance.

5\. Polish

Lighting, effects, sound, transitions and final QA.

### 17.2 Asset acceptance requirements

Every asset should have an explicit definition of done.

For example, an enemy sprite sheet is not complete merely because the image has been generated.

It is complete when:

- All required frames are present.
- The frame layout is correct.
- The transparent background is correct.
- The animation plays correctly.
- The feet remain anchored.
- The sprite faces the correct directions.
- The hitbox matches the visible body.
- The enemy works in the actual arena.

This will save a lot of time.

# PART XIII — AI agent development workflow

## 20. How I recommend using Codex and Antigravity

This section is particularly important because we should not allow AI agents to independently redesign the game while implementing it.

The biggest danger in AI-assisted game development is architectural drift.

An agent might fix one issue by creating another combat controller, duplicate an existing state manager or replace an existing system unnecessarily.

We need a controlled workflow.

### 20.1 Divide the work between agents

| Agent       | Responsibility                                                        |
| ----------- | --------------------------------------------------------------------- |
| Codex       | Codebase inspection, implementation, debugging                        |
| Antigravity | Visual inspection, scene testing and integration assistance           |
| You         | Gameplay testing, artistic decisions and acceptance                   |
| Me          | System specifications, prompts, design reviews and debugging guidance |

### 20.2 Every coding task should follow four steps

1\. Inspect

Agent examines the existing implementation and identifies the relevant systems.

2\. Plan

Agent explains exactly which existing files and systems it intends to modify.

3\. Implement

Agent makes the smallest changes needed without replacing working systems.

4\. Verify

Agent runs the project, checks the relevant behaviour and reports what was tested.

Don't let an agent jump directly into rewriting combat because an attack animation is not working.

First determine whether the problem is in the animation, hitbox, state machine or input handling.

# 23. My final recommendation

There is one lesson from Hades that I want us to take particularly seriously.

Don't confuse the amount of content in a game with its depth.

Hades has six weapons, numerous gods, hundreds of upgrade combinations, many enemies, bosses and enormous amounts of dialogue.

But the underlying experience rests on a relatively compact set of interconnected systems.

For Kaliyuga, our vertical slice has a different opportunity.

We have:

- One central playable character.
- One primary weapon identity.
- Three stances.
- Existing combat abilities.
- A defined enemy roster.
- Two major bosses.
- A central hub.
- A focused story sequence.
- A distinctive art direction.

That is enough to create a convincing vertical slice if the implementation is polished.

I would much rather see someone play 30 minutes of Kaliyuga and say:

The combat feels excellent, the bosses are memorable, the world looks beautiful, and I want to play more.

That is a much stronger result than showing someone a large number of unfinished systems.

The order I would personally enforce is:

1. Make Rudra feel excellent.
2. Make one enemy encounter excellent.
3. Make Dundubhi excellent.
4. Make Vrikodara excellent.
5. Connect everything through the hub and story.
6. Polish the entire experience.

This is the Hades lesson worth applying to our game.
