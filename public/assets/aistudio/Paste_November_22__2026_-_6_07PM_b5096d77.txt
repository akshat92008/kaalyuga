# PART A — PROJECT RULES

## A1. Mission

Create the most visually polished combat prototype feasible inside Google AI Studio Build.

The result must combine:

- Responsive, satisfying combat.
- Beautiful, original elemental VFX.
- Convincing Parashu weapon movement.
- Accurate hit synchronization.
- Cinematic impact feedback.
- Readable isometric presentation.
- Reusable code suitable for later integration.
- Performance-aware implementation.

The aesthetic ambition is the spectacle and fluidity associated with premium anime action games, adapted into an original dark Indian mythological visual language.

**The goal is not to copy Demon Slayer. The goal is to achieve comparable visual clarity, dramatic movement, power and elegance through Kaliyuga's own designs.**

## A2. Strict environment limitations

Neon is working inside Google AI Studio Build.

Therefore:

1. Do not assume access to the Kaliyuga GitHub repository.
2. Do not invent information about existing game source files.
3. Do not claim to have fixed bugs in the original game.
4. Do not attempt repository branches, commits or pull requests.
5. Do not require Blender or Unreal Engine.
6. Do not depend on paid external APIs.
7. Do not require proprietary art, models or audio that has not been supplied.
8. Do not pretend a static illustration is an actual animated effect.

Where original models or animations are unavailable, create clearly labeled temporary replacements.

The replacement assets should have similar visual proportions and attachment points so they can be exchanged during integration.

## A3. Required deliverable

Produce **one playable application** containing the complete Phase 0 foundation and Phase 1 effects.

It must include an interactive arena, a controllable warrior, an enemy target, working attack states, all required elemental attacks, a quality selector and an optional developer inspection panel.

All effects must be rendered by the running application.

A collection of demonstration videos, concept images or separate experimental pages is not an acceptable substitute.

# PART B — PHASE 0: COMBAT FOUNDATION

## P0.1 — Project architecture

**Objective:** Establish a clean structure before creating complex VFX.

Use React and TypeScript for the application and Three.js with WebGL for real-time rendering.

The main scene should not be recreated whenever an attack happens or a React state variable changes.

Organize the application into these logical modules:

| Module | Responsibility |
|---|---|
| GameScene | Three.js renderer, scene lifecycle and animation loop |
| GameCamera | Isometric camera, framing and shake |
| InputController | Keyboard and mouse input |
| PlayerController | Movement, stance and action states |
| CombatController | Attack scheduling, damage and recovery |
| WeaponTracker | Parashu transforms and blade-tip trajectory |
| EnemyController | Dummy enemy health, posture and reactions |
| VfxDirector | Starts, updates and ends elemental effects |
| EffectPool | Reuses particles, geometry and effects |
| ElementRenderers | Fire, wind, thunder, water and guardian visuals |
| AudioDirector | Optional original sound playback and impact timing |
| PerformanceMonitor | FPS, frame times, effect counts and quality settings |
| DebugPanel | Visual test controls and diagnostics |

**Architecture rule:** Combat logic must remain separate from VFX rendering.

The player should still be able to move, attack and damage the dummy when decorative effects are disabled.

### Acceptance gate

- Application opens without fatal errors.
- A Three.js scene renders successfully.
- Input works.
- The renderer updates continuously.
- Scene objects are not recreated unnecessarily.
- Modules have clear responsibilities.

## P0.2 — Establish the isometric presentation

Create a small, atmospheric combat arena inspired by Kaliyuga's Charnel Plains.

The arena should include:

- Ancient cracked stone flooring.
- Ash-darkened terrain.
- Scattered bronze architectural debris.
- Subtle distant embers.
- A restrained crimson atmospheric glow.
- Readable shadows beneath characters.
- Enough empty space to inspect combat effects.

The environment is a **testing stage**, not a replacement for the existing game's MP4 arenas.

### Camera requirements

Use an orthographic or carefully controlled perspective camera that reads as isometric 2.5D.

Its composition should resemble a playable action roguelite, not a close-up third-person action game.

Rudra and his target must remain large enough to inspect without misrepresenting how effects look at actual gameplay scale.

Implement two inspection modes:

**Gameplay mode:** Normal isometric distance, used for all mandatory acceptance tests.

**Detail mode:** Closer inspection for weapon trajectories, shaders, particles and attachment points.

A beautiful effect visible only in Detail mode fails gameplay-readability acceptance.

### Acceptance gate

Rudra, the enemy, the ground and their effects must remain clearly distinguishable at normal gameplay distance.

### Rudra

If an actual Rudra model is not available, create a stylized temporary warrior with:

- Dark bronze and bone-colored armor.
- Crimson cloth accents.
- Readable head, shoulders, torso, arms and legs.
- Strong silhouette.
- A visible two-handed or one-handed Parashu grip appropriate to the attack.
- Distinct idle and attack poses.

The temporary model is not expected to match the finished Rudra art.

### Parashu

Create a recognizable axe with:

- A visible blade.
- A clearly defined grip or hand attachment.
- A defined blade root.
- A defined blade tip.
- A blade orientation suitable for tracking attacks.

The weapon should rotate and translate during attacks, not simply sit in the player's hand while effects animate independently.

### Weapon attachment interface

Every frame, the system must make the following information available:

- Player world position.
- Player facing direction.
- Weapon world transform.
- Blade root position.
- Blade-tip position.
- Previous-frame blade-tip position.
- Weapon-tip velocity.
- Current attack identifier.
- Normalized attack progress from 0 to 1.

This is the foundation of synchronization.

**Do not build the main VFX using fixed arbitrary offsets from the character.**

## P0.5 — Combat state machine

Implement a finite-state combat controller.

Suggested states:

| State | Description |
|---|---|
| Idle | Standing ready |
| Moving | Walking or repositioning |
| Windup | Attack anticipation |
| Active | Damage-producing attack frames |
| Recovery | Attack completion and return to control |
| Dashing | Short evasive movement |
| Parrying | Defensive window |
| Staggered | Hit reaction |
| Guardian | Temporary transformed combat state |

These are combat states, not separate visual effects.

### Attack timing

Each attack must have an explicit timeline:

**Windup → Active frames → Recovery**

Use provisional timings appropriate to the feel of each stance:

| Stance | Light attack target | Heavy attack target | Intended feel |
|---|---|---|---|
| Smash | Roughly 450–550 ms | Roughly 850–1,000 ms | Brutal and weighty |
| Pillar | Roughly 400–500 ms | Roughly 750–950 ms | Controlled and grounded |
| Thrust | Roughly 350–450 ms | Roughly 700–850 ms | Quick and piercing |

These are initial prototype values, not canonical Kaliyuga timings. Make them configurable.

Damage must occur only during the intended contact window.

The character should not deliver multiple unintended hits merely because a collision overlaps across several frames.

### Acceptance gate

Every light and heavy attack must demonstrate a recognizable anticipation, contact and recovery.

## P0.6 — Create three distinct stance animations

### Smash

**Light attack:** Broad, committed axe swing with a visible follow-through.

**Heavy attack:** Strong anticipation, large sweeping or overhead movement, powerful contact and substantial recovery.

The heavy weapon should feel as though it has mass.

### Pillar

**Light attack:** Compact, controlled attack emphasizing stability.

**Heavy attack:** Deliberate, authoritative movement with a powerful grounded finish.

The pose should communicate control rather than spinning recklessly.

### Thrust

**Light attack:** Fast directional strike.

**Heavy attack:** Charged, linear piercing motion with a decisive endpoint.

The silhouette must communicate a different attack intention from Smash.

### Animation standard

No attack should be only an effect playing while the character remains static.

Animation and effects must be coordinated, even if the initial motion uses procedural posing or temporary animation clips.

## P0.8 — Implement weapon contact synchronization

This is the most important technical gate in Phase 0.

Implement a **WeaponTracker** that samples the weapon's world-space position throughout the attack.

### Required behavior

At attack start, register the attack identity and animation timeline.

During the attack, record the blade root and tip positions at each update.

Use recent weapon positions to create directional trail geometry.

At the active frame, detect the intended contact position.

Trigger the impact effect at the contact point.

During recovery, stop creating active trail segments and allow existing visuals to dissipate.

### Failure cases to detect

- Effects beginning before the weapon moves.
- Trails appearing behind the character while the blade moves forward.
- Impact effects appearing at a fixed screen coordinate.
- The same impact triggering repeatedly.
- Trails continuing after the attack has finished.
- VFX jumping when the player changes direction.
- Incorrect effect alignment after dashing.

### Acceptance gate

With all effects reduced to simple white diagnostic trails, the geometry must visibly follow the weapon.

If this fails, do not proceed to complex elemental effects.

- Configurable hit-stop.

- Optional ground dust.

The important part is timing and coordination, not visual extravagance.

Use different feedback strength for light and heavy attacks.

Heavy attacks should have a more noticeable impact but must not cause the screen to shake continuously.

Provide a Reduced Motion option.

### Acceptance gate

The player should clearly distinguish a light hit, heavy hit, missed hit and blocked hit.

# PART C — PHASE 1: ELEMENTAL VISUAL DEVELOPMENT

## P1.1 — Establish Kaliyuga's visual language

Before developing individual elements, create a unified artistic system.

### Core principles

**1. Flow:** Every effect should travel along an intentional trajectory.

**2. Power:** Heavy attacks require stronger composition and impact.

**3. Readability:** Rudra, the enemy and the collision remain visible.

**4. Material identity:** Fire, water, lightning and wind must behave differently.

**5. Layering:** Effects should have foreground, core and residual components.

**6. Restraint:** Visual effects should not overwhelm combat indefinitely.

**7. Originality:** Indian mythological imagery should influence the shape language, without simply borrowing recognizable animation sequences from other media.

### Color direction

| Element | Primary palette | Visual identity |
|---|---|---|
| Agni | Sindoor red, fiery orange, bright gold | Calligraphic flames and violent heat |
| Vayu | Emerald, jade, luminous mint | Bladed wind and flowing currents |
| Vajra | Electric blue, violet, white-gold | Sharp branching energy and flashes |
| Varuna | Deep blue, turquoise, silver-cyan | Flowing ribbons and water-serpent movement |
| Guardian | Deep crimson, antique bronze, near-black | Spectral cleaves and wrathful energy |

Use gradients and material variation rather than one flat color for an entire effect.

---

## P1.2 — Create reusable VFX primitives

Do not hand-code an entirely separate effects engine for each element.

Create reusable primitives with independent animation behavior:

| Primitive | Purpose |
|---|---|
| BladeRibbon | Continuous weapon-following trails |
| ArcMesh | Wide curved directional shapes |
| ImpactBloom | Brief light burst at contact |
| DirectionalBurst | Emission along the strike direction |
| ParticleEmitter | Sparks, droplets, debris, motes |
| Shockwave | Grounded or outward-moving wave |
| DistortionLayer | Controlled localized refractive effects |
| ResidualField | Short-lived atmospheric aftermath |
| LightningBranch | Branching energy geometry |
| FluidRibbon | Flowing segmented water shapes |
| SpectralSlash | Guardian-specific large energy blade |
| GroundContact | Dust, cracks or elemental reactions |

Use pooled resources and share geometry/materials when possible.

Avoid creating hundreds of independent React components for particles.

VFX primitives should receive world-space coordinates, attack direction, timing and quality settings from the game controller.

---

## P1.3 — Standard elemental attack structure

Every elemental attack should be composed of five moments.

### Moment 1 — Anticipation

A short hint of the element appears near the weapon or warrior.

For example, flame gathers along the axe edge before a heavy Agni strike.

This should create anticipation without firing the main attack too early.

### Moment 2 — Weapon movement

A flowing blade trail appears along the actual Parashu trajectory.

The direction of the visual effect must reflect the direction of the weapon.

### Moment 3 — Contact

The strongest effect appears when the weapon hits its target or reaches the intended attack endpoint.

This is where the major impact flash and contact feedback occur.

### Moment 4 — Secondary release

A larger elemental shape expands from the strike direction.

Examples include a flame wave, emerald gale, electrical shock or water surge.

### Moment 5 — Dissipation

The effect breaks apart into element-specific particles or residual energy.

It must not freeze, abruptly turn into a rectangle or disappear unnaturally.

**Timing and choreography are more important than the total number of particles.**

# PART D — ELEMENT-SPECIFIC PRODUCTION

## P1.4 — AGNI: FIRE SYSTEM

### Visual personality

Agni should feel ferocious, aggressive and ceremonial.

The effect should resemble a powerful painted flame brought to life, not a circular particle emitter.

### Agni light attack

Build three visual layers:

**Primary layer:** A bright, curved orange-gold blade trail following the weapon.

**Secondary layer:** Red-orange flame tongues flowing outward from the swing.

**Residual layer:** Fine sparks and embers fading behind the strike.

The trail should be clearly visible at gameplay zoom.

Avoid excessive smoke during normal light attacks.

### Agni heavy attack

Build a seven-part sequence:

1. Warm red glow begins around the axe edge.
2. Flames gather and stretch in the direction of anticipation.
3. A massive calligraphic fire arc follows the heavy swing.
4. At contact, a concentrated golden-white burst appears.
5. A directional wall or crest of flame erupts from the impact.
6. Sparks and fragments scatter along the attack's momentum.
7. The burst collapses into embers, dark smoke wisps and fading glow.

The heavy attack should feel substantially more powerful than its light counterpart.

### Smash variant

Broad flame fan and destructive ground contact.

### Pillar variant

Tightly controlled, forceful flame column or grounded eruption.

### Thrust variant

Narrow, piercing flame spear or concentrated forward stream.

### Rejection criteria

- Large flat orange circles.
- Uniform spirals.
- Flame spawning far from the axe.
- Static textures pasted over the player.
- Excessive bloom hiding the model.
- Persistent bright effects covering enemy attacks.

---

## P1.5 — VAYU: EMERALD WIND SYSTEM

### Visual personality

Vayu should feel fast, precise and elegant.

It should contrast strongly with Agni.

### Vayu light attack

A thin emerald edge accompanies the axe movement.

A flowing wind ribbon follows, with small jade energy fragments and directional air streaks.

The effect should feel sharp rather than explosive.

### Vayu heavy attack

1. The air around the blade begins to distort.
2. Narrow wind streams wrap around the weapon.
3. Rudra performs the heavy strike.
4. A wide, beautiful emerald slash expands along the actual swing.
5. Multiple layered currents travel forward.
6. A forceful gust impacts the ground or enemy.
7. Thin green ribbons and motes dissipate.

The heavy attack should have visible depth and a striking silhouette.

### Smash variant

Large, fan-shaped gale cleave.

### Pillar variant

Compressed turbulent wind with a forceful release.

### Thrust variant

Thin high-velocity wind lance with trailing lines.

### Rejection criteria

- Green smoke clouds with no direction.
- Repeated circular particle rings.
- Trails detached from the weapon.
- Effects too transparent to see at normal camera distance.
- Excessively large green areas obscuring enemies.

---

## P1.6 — VAJRA: THUNDER SYSTEM

### Visual personality

Vajra should feel instantaneous, precise and devastating.

Unlike fire and water, lightning should contain hard-edged branches and very brief, powerful luminosity changes.

### Vajra light attack

A tight electric glow runs along the axe.

Short lightning branches follow the blade during movement.

At contact, a white-blue flash and a small cluster of sparks appear.

The effect rapidly dissipates.

### Vajra heavy attack

1. Blue-violet energy gathers along the weapon.
2. Small electrical arcs flicker during anticipation.
3. A luminous, directional strike follows the weapon motion.
4. Lightning branches connect the blade with the intended contact area.
5. A high-intensity contact flash occurs.
6. Large electrical branches propagate briefly along the impact direction.
7. Residual sparks flicker and decay.

### Smash variant

Wide thunder cleave and grounded electrical branches.

### Pillar variant

Concentrated shock pulse with controlled radial discharge.

### Thrust variant

Narrow, fast lightning penetration with a sharp endpoint flash.

### Rejection criteria

- Random lightning unrelated to the hit.
- Long branches remaining on screen after the strike.
- Whiteout obscuring all combat information.
- Excessive bloom destroying the underlying color design.
- Every lightning effect appearing identical regardless of attack type.

---

## P1.7 — VARUNA: WATER SYSTEM

### Visual personality

Varuna should feel fluid, graceful and overwhelming.

Water must have visible direction, weight and flow.

### Varuna light attack

A flowing cyan-blue ribbon emerges along the axe trajectory.

Thin water streaks follow the blade.

At contact, a crisp splash breaks outward.

Small droplets scatter and disappear naturally.

### Varuna heavy attack

1. Water-like energy gathers around the Parashu.
2. Flowing bands stretch toward the expected strike path.
3. The axe produces a large directional water ribbon.
4. The flowing ribbon develops into a powerful wave or stylized serpent-like crest.
5. Contact produces a dense splash and luminous blue impact.
6. Secondary water streams spread outward.
7. Droplets and residual mist dissolve.

The serpent motif must convey forward motion through curves, head direction and tapering flow.

It should not resemble a static blue donut.

### Smash variant

Large crashing wave.

### Pillar variant

Strong vertical water surge.

### Thrust variant

Fast, narrow water-serpent strike.

### Rejection criteria

- Static blue rings.
- Solid blue geometry with no surface variation.
- Water moving independently of the weapon.
- Fluid effects looking identical to recolored fire.
- Persistent mist hiding characters.

---

## P1.8 — KALA-BHAIRAVA: GUARDIAN RAGE

### Visual personality

Guardian rage must feel terrifying, supernatural and authoritative.

This effect should be visually distinct from the four regular elements.

Use deep crimson, antique bronze, black ink-like shadows and carefully placed white-hot accents.

### Guardian light attack

A sharp crimson spectral blade follows the weapon.

Dark energy trails briefly separate from the edge and collapse after impact.

The attack should feel unnaturally powerful without becoming visually chaotic.

### Guardian heavy attack

1. The guardian's spectral energy intensifies.
2. A much larger weapon-shaped energy silhouette forms around the actual strike.
3. Rudra executes the heavy animation.
4. A massive crimson cleave follows the blade trajectory.
5. The cleave strikes at the intended contact point.
6. A dark-crimson energy burst and bronze fragments expand.
7. The energy tears into smaller ink-like remnants.
8. The visual field returns to normal, preserving combat readability.

### Mandatory restrictions

Do not replace Rudra with an unanimated glowing square.

Do not introduce arbitrary guardian horns, armor changes or character redesigns.

Do not create a separate combat control system.

Do not spam the guardian name across the screen.

Do not obscure Rudra and all enemy telegraphs for the entire effect duration.

Guardian rage may have dramatic visual scale, but its performance cost must remain bounded.

# PART F — INTEGRATION-READY DESIGN

## P1.10 — Effect event interface

The finished VFX library must not depend on the demo's placeholder character.

The integration contract should expose the following event types:

### Attack start

Information supplied by the combat system:

- Attack ID.
- Player or character ID.
- Stance.
- Element.
- Light or heavy classification.
- Attack duration.
- Starting transform.
- Target direction.

### Weapon pose update

Information supplied every update:

- Blade root world position.
- Blade-tip world position.
- Previous blade-tip position.
- Weapon orientation.
- Normalized attack progress.

### Attack contact

Information supplied when damage/contact is resolved:

- Attack ID.
- Contact world position.
- Contact normal or direction.
- Hit or miss.
- Enemy identifier.
- Impact intensity.

### Attack finish

Information supplied when the strike ends:

- Attack ID.
- Whether the animation completed or was interrupted.
- Whether lingering effects should be shortened or stopped.

### VFX update

The system advances all active visual effects using elapsed time and the configured quality preset.

### VFX cleanup

The system releases effect resources when complete and safely handles scene unload or restart.

**Architectural rule:** Neon builds a reusable visual layer. Existing Kaliyuga gameplay should remain the authority on damage, stamina, posture and combat rules when integration occurs.

# PART G — TECHNICAL VISUAL QUALITY

## P1.11 — Trail rendering

Weapon trails should use actual sampled positions.

Use smooth interpolation or curve construction where necessary to avoid gaps.

The trail must maintain continuity when the weapon moves quickly.

Implement appropriate width variation:

- Narrow at trail endpoints.
- Thickest near the most important portion of the strike.
- Tapered during dissipation.

Use gradient coloring and transparency carefully.

Avoid visible square edges, stretching artifacts and abrupt mesh cuts.

Do not allow additive blending to create large opaque rectangular regions.

## P1.12 — Shader quality

Start from stable, correctly rendered materials.

Add custom effects selectively for:

- Gradient transitions.
- Animated flow.
- Edge glow.
- Dissolve behavior.
- Distortion.
- Localized heat or energy movement.
- Procedural noise where useful.

A shader is only valuable if it improves the actual result.

Avoid introducing complex full-screen shader pipelines simply because they sound impressive.

## P1.13 — Effect layering

Each heavy attack should have an identifiable composition:

**Core shape:** The main elemental weapon-following form.

**Secondary shape:** The larger power release.

**Contact accent:** A precisely timed impact flash.

**Residual movement:** Sparks, droplets or energy fragments.

**Environmental accent:** A restrained ground reaction.

Every layer must contribute visually. Remove redundant layers that make the result muddy.

# PART H — PERFORMANCE ENGINEERING

## P1.14 — Quality profiles

Provide at least three quality presets.

| Feature | High | Medium | Low |
|---|---|---|---|
| Main blade trails | Full detail | Reduced segments | Simplified |
| Secondary particles | Rich | Moderate | Minimal |
| Distortion | Selective | Limited | Disabled |
| Bloom | Controlled | Reduced | Minimal/off |
| Residual effects | Full | Shorter | Very short |
| Texture resolution | Appropriate | Reduced where feasible | Conservative |
| Effect overlap | Bounded | More restricted | Strict |

Choose actual numeric limits based on observed render performance.

Do not claim a particular particle count guarantees 60 FPS.

### Performance requirements

- Reuse particle and mesh instances where possible.
- Avoid unnecessary material creation during attacks.
- Limit active simultaneous heavyweight effects.
- Clean up finished geometry and GPU resources.
- Clamp unreasonable frame-time deltas.
- Avoid shader compilation during the most important impact frame when practical.
- Test repeated attacks and scene resets.
- Monitor actual frame time, not only average FPS.

### Intended performance target

The aspirational target is smooth 60 FPS gameplay at the intended resolution.

The 60 FPS frame budget is approximately 16.7 milliseconds, but meeting that number must be measured, not assumed.

Where 60 FPS is unattainable, the application should degrade effect complexity rather than break gameplay.

MacBook M3 Air acceptance must occur after export and local execution. AI Studio preview performance is not sufficient evidence of target hardware performance.

# PART I — VISUAL REVIEW AND TESTING

## P1.15 — Mandatory testing sequence

Do not merely take one screenshot per element.

### Test group A — Functionality

Verify movement, attacks, stances, elements, rage switching, dashing, parrying and recovery.

### Test group B — Synchronization

Inspect each element with blade-tip tracking visible.

Compare the intended blade trajectory with the rendered trail.

Check the impact frame.

### Test group C — Readability

Test all attacks at normal gameplay zoom.

Confirm the character, target, attack direction and enemy reactions remain understandable.

### Test group D — Overlapping effects

Trigger repeated attacks and several effects in a controlled stress-test scenario.

Check for GPU stalls, particle buildup, visual clutter and cleanup failures.

### Test group E — Appearance

Review Agni, Vayu, Vajra, Varuna and Guardian separately.

Determine whether the element is immediately recognizable without reading its name.

### Test group F — Edge cases

Test changing elements and stances during recovery.

Test dashing before and after attacks.

Test repeated heavy attacks.

Test attacks that miss.

Test clearing the arena while effects are active.

Test switching quality presets.

Test pausing and resuming.

### Test group G — Long-running stability

Run repeated combat sequences, then verify effects have returned to their expected inactive counts.

There must be no steadily accumulating trails, particle objects or other obvious resource leaks.

## P1.16 — Actual visual acceptance standard

For each elemental attack, assess six qualities.

| Criterion | Question |
|---|---|
| Synchronization | Does the VFX genuinely follow the weapon? |
| Beauty | Are its shapes, colors, movement and layering visually polished? |
| Power | Does the heavy attack feel significantly stronger than the light attack? |
| Readability | Can the player still understand the action? |
| Identity | Is the element visually distinct? |
| Performance | Does it render without unacceptable instability? |

Do not mark an attack complete until all six have been reviewed.
